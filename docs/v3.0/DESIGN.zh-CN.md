日期：2026-09-08。分支：`v3.0`，从包含 v2.1 实验归档的 `a65d89c` 建立。本文定义的首版流程已实现并完成 CPU 开发验证；尚无 v3.0 正式 GPU 结果。实际命令见[离线运行手册](RUNBOOK.zh-CN.md)。

设计依据为用户已认可的《数据集与自动 KV 选层重设计建议》（2026-09-08）、[共同语言](../../CONTEXT.md)、[v2.1 修正说明](../v2.1/CORRECTIONS.zh-CN.md)、现有代码与[已归档的 v2.1 结果](../../results/v2-20260908T024604.457854Z/bf1713af667c14f3-QUALITY-v2.zh-CN.md)。本文完整记录实施所需决策，不依赖工作区中被 Git 忽略的研究草稿。具体改动顺序见[实现计划](IMPLEMENTATION-PLAN.zh-CN.md)。

## 1. 项目目标与版本边界

给定合理且预先定义的任务分布，离线自动选择 BF16 KV 层集合 `S`，其余层使用 FP8 E4M3 KV。在独立测试集上，相对全 BF16 的质量下降不超过预定阈值，并在相同 KV 显存预算下取得至少 `1.5×` 的实测 KV token 容量。

优化对象是 KV Cache，模型权重不变。输出可以是全 FP8，也可以是中间混合配置；无需为了展示混合精度而强行保留某一层。吞吐提升、算法首创、所有任务上的普适最优均不属于主验收。

v2.1 已证明一次 `P1=[17]` 配置在旧协议下通过，但旧数据只有 45 条，其中独立留出集仅 18 条。部分任务 BF16 得分很低，四层组筛选还将后续单层探测限于八层，不能支持可靠的数据分布与选层方法结论。v1.0 的 full 搜索是全层单独恢复后的静态排序，也不是每轮重新测量条件收益的贪心。

v3.0 作以下替换，不追溯改变历史版本的评分与结论：

| 方面 | v3.0 决策 |
|---|---|
| 数据 | 新建正式 1280 个不同问题实例；实验集 256、测试集 1024，另有开发样本 |
| 任务 | 多键检索、多值检索、单跳 QA、有限多跳 QA，均覆盖四档长度 |
| 选层 | 逐轮扩展所有剩余层的束搜索，默认宽度 2，附反向删层 |
| 成本 | 用 32、96、256 条嵌套实验样本分配评估预算；复用已经完成的回答 |
| 结论 | 实验集选配置，冻结配置后独立测试；同时报告点估计、区间与实测容量 |

## 3. 数据设计

### 3.1 任务与难度

本项目构造自定义的长上下文检索与有证据短答案 QA 协议，采用 [RULER](https://arxiv.org/html/2404.06654v2) 的任务思路。数据来源、难度和组合经过调整，不称为官方 RULER 总榜结果。

| `task` | 构造方式 | 首版难度与评分 |
|---|---|---|
| `multi_key` | 在自然背景中放入多组唯一键值，查询多个不同键 | 默认共 32 组键值，查询其中 3 个键；按键值配对 F1 评分 |
| `multi_value` | 同一目标键在不同位置对应多个唯一值，同时放入其他键的干扰记录 | 默认目标键 4 个值、28 条干扰记录；按目标值集合 F1 评分 |
| `qa_single` | 从 SQuAD v2.0 的可回答问题中选择问题，完整保留答案所在段落，加入无关文档 | 使用短答案提示；对合法答案别名取最高 token F1 |
| `qa_multi` | 从 HotpotQA 的有答案样本中选择有限多跳问题，保留全部支持文档与证据链 | 使用短答案提示；对合法答案别名取最高 token F1 |

SQuAD/HotpotQA 的版本、使用的原始 split、文件来源和筛选规则写入来源清单。初始来源为 SQuAD v2.0 的 train/dev 与 HotpotQA distractor 的 train/dev；它们只作为本项目的原料，本项目的实验/测试划分另行生成。数据适配参考 [RULER 官方 QA 生成器](https://github.com/NVIDIA/RULER/blob/main/scripts/data/synthetic/qa.py)，不依赖运行完整 RULER 框架。

检索题的键、值必须互不歧义，答案分布在上下文的不同位置，干扰记录中不能意外包含目标答案。多键题的配对错误不得因答案值都出现而得满分。多值题把重复输出去重，多报错误值会降低 precision。QA 使用预先定义的规范化与别名，保留完整原始输出；不借助另一个 LLM 临时判分，也不因模型解释过长而事后更换提取器。

BF16 开发阶段观察任务均分、错误类型、输出截断和长度效应。`0.6–0.9` 可作为 QA 等中等任务的可解性参考，检索任务接近满分不自动失效；这个区间不是逐题筛选规则，也不是正式命令的启动条件。不根据“BF16 对、FP8 错”挑题。旧 45 条样本只保留为历史与开发材料。

### 3.2 先划分来源，再生成问题

数据构造按以下顺序完成：

1. 读取本地来源文件，统一问题、答案、文档 ID 和证据关系。先按原始 ID、规范化文本消除重复；同一原始问题的改写和长度变体属于同一基础实例。
2. 将来源文档分配给 `development`、`experiment`、`test`。相同文档在不同来源中的重复记录尽可能合并；多跳题只有全部支持文档归于同一 split 才可入选。来源分配使用固定种子，不能先生成完再随机拆行。
3. 在各 split 中按明确的问题索引取样，分配到任务与长度单元。一个问题只进入一个长度；共享证据的来源组留在同一任务与长度单元，优先每组取一个问题。来源不足时报告缺少哪个单元及原因，不复制题目补数，也不截断必要证据。
4. 从对应 split 的自然文本池加入干扰背景。背景池也按文档隔离，正式实验与测试不共享原始背景文档；同 split 内复用背景的情况记录在元数据中。检索题同一基础场景的派生题保持同组，不能仅换随机值就把同一实例跨 split 使用。
5. 用服务器已有目标 tokenizer 和 chat template 构造并计数。仅缩放或裁剪非证据背景，使实际输入落入目标长度容差；保留完整问题、答案证据和生成空间，`prompt_tokens + max_tokens <= max_model_len`。

这里的独立性指避免本项目选择过程与测试相互泄漏，不声称这些公开 QA 从未出现在模型预训练中。不同题若仍共享证据或基础场景，记录 `source_group_id`，不能把它们当作同等数量的独立来源。

为便于分层重采样，生成器使一个证据/基础场景组只属于一个任务与长度单元。HotpotQA 两组已用文档若会把不同单元连接起来，跳过该来源组合；这是分组取样规则，不依据模型答题结果。自然背景复用率单列报告，区间的解释以本次背景池与抽样设计为条件，不夸大对所有自然文档的外推能力。

### 3.3 嵌套实验前缀与文件合同

实验集每单元 16 题先固定组内顺序，再按 16 个单元轮转交织。因此前 32、96、256 题分别包含每单元 2、6、16 题。前缀在任何候选运行前确定，候选不能自行抽题；测试集不参与前缀构造。

正式生成文件为 `data/v3.0/quality/experiment.jsonl`、`test.jsonl` 和数据清单；开发样本放在独立目录。大体积来源和生成文本在本地保留、随实验输入归档，不直接塞入常规源码提交。

每条正式样本至少记录：`sample_id`、`source_question_id`、`source_group_id`、`split`、`task`、`length_bucket`、`source_document_ids`、`evidence_document_ids`、`background_document_ids`、`user_prompt`、`expected_answers`、`prompt_tokens`、`max_tokens`、`scorer`、生成种子及证据位置。数据清单记录来源版本、模板、计数方式、每单元题数与独立来源组数。

数据准备时检查缺失答案、重复 ID、跨 split 证据、证据被裁掉和长度越界；这些直接影响实验正确性。运行时读取已生成数据，只做必要的一致性检查，不重新下载、重新随机生成或重跑开发实验。

## 4. 质量、容量与主验收

### 4.1 质量计算

单题得分 `q_i(S)` 归一化到 `[0,1]`，BF16 参照为 `P32`。设 `t` 为任务、`l` 为长度：

```text
Q_(t,l)(S) = 对该任务与长度单元中的单题得分求均值
Q_t(S)     = (1/4) × sum_l Q_(t,l)(S)
Q_all(S)   = (1/4) × sum_t Q_t(S)
Delta_j(S) = Q_j(P32) - Q_j(S)
```

完整数据中每单元题数相同，这也等于各任务直接求均值后等权平均；公式明确保留分层权重，防止缺失样本或重采样时悄悄改权重。`j` 包括总分与四任务，`epsilon_all=0.01`，其余 `epsilon_t=0.02`，均为绝对分数差而非相对百分比。

配置在完整实验集上的可行条件是全部 `Delta_j <= epsilon_j`。不得使用一个任务的改善抵消另一个任务超出其容差的下降。逐长度、逐任务与长度单元均报告，但首版不把每个长度单独加成硬约束；若以后服务范围需要这样的约束，应在新实验前改协议。

BF16 和候选必须对同一组样本比较。模型正常生成的错误答案、空答案和 `finish_reason=length` 均保留并按规则计分，不能重试直到答对。HTTP/进程错误属于未完成请求，不能通过删行或缩小分母获得通过结果。

不沿用旧版“Easy 必须全对”的条件，也不设 BF16 必须超过 0.6 的门槛。但如果 BF16 在一个主任务的全部样本上得分为零，应记录 `reference_degenerate`：该任务缺乏可测的参照质量，不能用两边都为零声称质量得到保留。保留原始点估计与诊断，不自动重写题目或开始新一轮选层。

### 4.2 容量计算

对本模型，一层 BF16 KV 每 token 为 `2 × 8 × 128 × 2 = 4096` bytes，一层 FP8 KV 为 2048 bytes：

```text
B(S) = 65536 + 2048 × |S|                      bytes/token
C_theory(S) / C_theory(P32) = 64 / (32 + |S|)
k_max = floor(64 / 1.5 - 32) = 10
```

目标是在质量约束内尽量减少 `|S|`，而不是最大化总分。`k=10` 理论倍率约为 1.524，`k=11` 约为 1.488，因此当前搜索到 10 层为止。该推导用于预算剪枝；主验收仍读取同环境、同 16 GiB 预算的真实 vLLM `KV token capacity`，不以理论值冒充实测值。

每次服务启动都记录实际 dtype、KV 预算与容量。报告采用正式测试对应的 P32 与候选容量；若同配置不同启动容量不一致，保留各次测量并解释，不能挑较大的候选值与较小的参照值拼成倍率。缺少容量日志时保留质量结果并标为容量未验证，无需为继续质量推理额外运行容量冒烟。

### 4.3 独立测试与区间

正式测试前写出冻结的层集合与选择依据。随后对测试集运行 P32、P0、最终候选，同配置去重；P0 被选中时只测两个端点。测试完整通过且实测容量达标，才设置 `technical_goal_passed=true`。

报告配对分差的 95% bootstrap 区间，默认 2000 次重采样，始终同步抽取 BF16 与候选的同一题。无共享来源时在 16 个单元内按题重采样；存在共享证据/基础场景时，在单元内按来源组重采样并带入组内所有题，报告组数。若某单元只有一个独立组，区间标为不可可靠估计，不用重复题制造窄区间。

`quality_passed` 表示预定点估计约束通过。区间上界仍超过容差时，报告“点估计达标，尚未证明该置信水平下的非劣性”。1024 题是首版资源预算，不自动保证证明 1% 边界；四任务区间也不冒称已经作过同时覆盖校正。区间用于说明证据强度，不新增人工批准或运行前统计门禁。

测试失败后保留失败结论，不能在同一测试集上调整层、阈值或提示再挑一个通过结果。后续迭代把该测试集视为已看过的数据，另行定义新测试；正式请求因传输故障中断后的原配置续跑不属于重新选择。

## 5. 自动选层算法

### 5.1 候选排序

在同一层数、同一样本前缀上定义：

```text
v_j(S) = max(0, (Delta_j(S) - epsilon_j) / epsilon_j)
V(S)   = max_j v_j(S)
W(S)   = sum_j v_j(S)
K(S)   = (V(S), W(S), -Q_all(S))
```

按 `K` 从小到大排序。最先减少最严重的违约，其次减少合计违约，最后比较总分。用 `1e-12` 仅处理浮点相等，不引入额外可调的质量容差。完整实验集仍严格按第 4 节判定可行。

父候选 `S` 扩展成 `S∪{i}` 时，同时记录该前缀上的 `Q_j(S∪{i})-Q_j(S)`，它是条件边际收益。多个父路径产生相同完整层集合只运行一次，并保留全部父路径关系。父配置已经全量评估，计算其前缀分数不增加请求。

### 5.2 前向束搜索与反向删层

```text
完整评估 experiment 上的 P32、P0
若参照数据不能形成有效比较：保存原因并结束选择
若 P0 可行：selected = P0，直接冻结
否则：beam = {空集合}

for k = 1 ... k_max:
    candidates = 去重({S 加入 i | S 属于 beam，i 不属于 S})
    使用 32 -> 96 -> 256 样本调度评估 candidates
    full = 本轮所有已经达到 256 条的候选
    若 full 中存在可行候选：
        selected = 其中按 K 排序最好的候选
        转入反向删层
    beam = full 中按 K 排序最好的至多 2 个候选

若未得到 selected：报告搜索预算内未找到可行解

反向删层：
    在完整实验集上逐一评估 selected 删除一个已保留层后的配置
    复用所有已存在的完整结果；若存在可行删除，选其中 K 最好的配置
    接受删除并再次检查，直到无法继续删除
    每次删除使层数减少，过程必然终止

冻结 selected；独立测试 P32、P0、selected；生成质量和容量结论
```

第一轮覆盖全部 32 个单层配置。后续每条路径都重新考虑所有尚未保留的层，不保留永久排除名单，不按层号分组。第一轮不重要的层仍可能在其他组合中得到高条件收益。

只在完整实验集上接受可行配置。提前淘汰的部分结果不能参与“最小可行层数”的确认。完全并列且必须限制完整评估后的束宽时，使用预先生成并记录的固定随机优先级；早期并列候选的处理见下一节。

在首个找到可行候选的深度停止扩展更大层数。反向删层仍有价值，因为删掉非末尾加入的层可能到达此前束搜索遗漏的较小集合；它不保证全局最小。`k=1` 且 P0 已完整失败时直接复用失败，不重复推理。

最大深度或显式资源预算耗尽而没有完整可行候选，只表示“本次预算内未找到”。实现允许用户设置选层与删层的请求数或墙钟预算，但默认不额外施加一个缺乏依据的小时上限；每次新评估前检查显式预算，保存已完成回答和搜索轨迹，不把预算耗尽写成不存在解或算法成功。

搜索预算不包含必要的端点与最终测试，报告分项及合计开销。若已经有完整可行候选，只是预算不足以继续删层，则冻结当前候选并注明删层未完成，仍可进行独立测试；不能声称它已经达到删除意义下的最小集合。资源预算结束与意外中断分别记录。

### 5.3 多保真调度的明确规则

多保真只改变问题数量，不缩短每题上下文，不改任务、输出预算、scale、后端或评分器。所有候选先运行固定前 32 题，晋级后只补缺少的题。

| 当前前缀 | 基础晋级数 `r` | 下一前缀 |
|---|---:|---:|
| 32 | `min(M, max(2, ceil(M/4)))`，`M` 为本轮候选数 | 96 |
| 96 | `min(M, 2)`，`M` 为到达此阶段的候选数 | 256 |

基础晋级数是节约预算的目标，不是必须只留下这些候选的硬上限。为落实“接近或并列时增加样本”，采用以下可复现的工程规则：

1. 按当前前缀的 `K` 选前 `r` 个，令第 `r` 个为边界候选。与边界三项点估计全部并列的候选一起晋级。
2. 对其他候选，与边界候选及 P32 做配对、按 16 个单元分层的 bootstrap，默认 2000 次；来源共享时沿用来源组重采样。所有比较使用同一组重采样索引，重算各次的 `K`。
3. 记录某候选 `K` 不差于边界 `K` 的重采样占比 `win_fraction`。该占比达到 `0.05` 时也晋级；低于该值才按本阶段证据淘汰。
4. 若当前前缀的独立来源组不足以估计比较，相关候选全部晋级。可比较但只在 bootstrap 中并列时，将并列算作不差于边界。
5. 到 256 条后不再自动扩大数据。所有全量候选先检查可行性，再决定最终候选或下轮的两条路径；保存每次晋级、淘汰与并列取舍理由。

`win_fraction` 是重采样下的排序比例，不是“找到最优配置的概率”，也不是有覆盖保证的淘汰检验。有限样本和反复自适应比较仍可能排掉好的候选，无法消除搜索误差。若差异不清楚，更多乃至全部候选会全量评估；不得悄悄用层号截断以兑现固定耗时。实现保留 `full` 评估调度作为直接全量评估的备选，便于在启动成本占主导时比较，但默认使用上述递增方案。

### 5.4 计算预算与可宣称的性质

若第一轮差异清楚，32 个候选的排程为：

| 阶段 | 回答数 | 服务启动数，按每次扩评重启估计 |
|---|---:|---:|
| 32 个候选各 32 条 | 1024 | 32 |
| 8 个候选各补 64 条 | 512 | 8 |
| 2 个候选各补 160 条 | 320 | 2 |
| 合计 | 1856 | 42 |

全部 32 个配置各跑 256 条需 8192 次回答，上述示例减少 77.34% 的回答数，但比一次全量评估多 10 次启动。不能称为已经实现 77.34% 的 GPU 时间加速。

深度 `k>=2` 每轮至多产生 `2×(33-k)` 个配置，第一轮为 32；搜索到 10 层的前向候选数上界为 518，另有反向删层。调度可能让所有候选全量评估，因此没有“固定几小时内找到解”的承诺。缓存与去重会降低实际请求数。

若 P1 第一轮即成功且按上表晋级，主流程共 `2×256 + 1856 + 3×1024 = 5440` 次回答、约 47 次启动。用旧 v2.1 的回答与控制开销粗估约 6.3 小时，仅用于初始排期，不含开发和额外对照；新任务的实测耗时应在两个端点完成后更新预测。

有限束宽可以漏掉协同组合，例如两层单独都无收益、同时保留才有效。质量也不保证随保留层数单调增加，不能套用单调次模条件下的贪心保证。本方案是在有限预算内找可行解的启发式方法；覆盖所有层的局部扩展不等于覆盖全部 `2^32` 个集合。

## 6. 运行器与结果复用

现有 `V2PolicyRunner.run_policy` 以完整 split 为复用单位。扩大传入样本列表会使旧结果不再满足整份校验，不能直接借此实现 32→96→256。v3.0 必须增加真正的逐样本续跑能力。

拟定接口为 `evaluate(policy, split, sample_ids)`：对当前运行输入、配置、生成设置和评分定义下的已有有效回答不再推理，只执行缺少的 ID；返回精确覆盖本次请求 ID 的评分视图。32→96→256 总请求量必须是 256，而非 384。

每次调用先写入本次评估范围，逐行落盘成功回答；服务启动日志分别保留在 `attempts/`。中断恢复时，只舍弃尚未写完整的尾行并保留诊断，不把已经完成的 31 条因为第 32 条失败而全部重跑。配置别名、搜索父路径不同但实际层集合相同，仍复用同一配置记录。

复用范围包含实际层 dtype、模型和 tokenizer、输入文本、输出预算、scale 与运行设置。不得跨数据版本、模型、精度布局或评分协议误用结果；沿用已有规范化配置标识，运行输入保存一份副本，不新增人工核验的多层 hash 清单。Git 提交号是可选来源信息，源码 ZIP 和本地未提交目录都能运行。

切换层精度时按已有后端能力重建引擎，不承诺权重常驻后的任意热切换。只缓存回答与评分，不跨策略共享 KV 张量。保留真实 dtype、prefix caching 关闭、prompt token 一致性检查；它们分别避免“实际没有混合精度”“对照受缓存影响”和“实际长度与数据定义不一致”。

每个回答记录原始文本、任务得分、`finish_reason`、输入/输出 token、请求耗时和错误；启动记录实际启动次数、KV 容量与耗时。暂时性 HTTP 错误至多自动重试一次并记录；启动失败、配置不支持或持续请求失败保存现场，结束为可恢复的运行失败，不无限重启。

## 7. 流程状态与证据

运行目录结构：

```text
runs/<run_id>/
  run-manifest.json             # 协议、实际环境、状态与来源说明
  inputs/                      # 实际源码、配置、数据与模板副本
  policies/<config_id>/
    experiment.jsonl
    test.jsonl
    attempts/                  # 每次启动与请求失败记录
  search-trace.jsonl            # 父集合、层数、前缀、得分、晋级/淘汰理由与开销
  selection.json               # 测试前写入的最终集合；包含 experiment 选择依据
  test-use.json                # 本次测试的问题与证据标识，用于识别跨运行重用
  completed-manifest.json
  report/QUALITY-v3.zh-CN.md
```

测试尚未开始时没有 `test.jsonl` 是正常状态。搜索代码只接收实验数据，测试执行器只接收已冻结的 `selection.json`；通过接口隔离测试反馈，不引入加密封存、签字或手工解锁步骤。主运行自动连接选择与测试。

`complete` 表示该次协议流程已得到终局结论，`technical_goal_passed` 表示主目标达标，两者分别记录：

| `status` | `complete` | 主目标达标 | 解释 |
|---|---|---|---|
| `passed` | true | true | 冻结候选测试质量与实测容量均达标，参照有效 |
| `test_quality_failed` | true | false | 实验集可行，测试质量未达标；保留候选和失败证据 |
| `test_not_independent` | true | false | 工作区中其他运行已经使用重叠测试问题或证据，本次仅作诊断 |
| `capacity_below_target` / `capacity_unverified` | true | false | 质量结果保留，容量不足或缺少实测证据 |
| `reference_degenerate` | true | false | BF16 某主任务全零，无法支持所需质量保留结论 |
| `no_feasible_within_budget` | true | false | 到达层数或显式搜索预算限制，未找到可行配置 |
| `interrupted` / `runtime_failed` | false | false | 未完成数据评估，可在相同输入与协议下续跑 |

未找到可行配置时不消耗独立测试集，也不为了凑齐报告启动 P32 测试。安全回退 P32 可单独记为部署建议，不写成自动选层取得容量收益。多个条件失败时报告分别列出质量、参照、容量与完整性状态，主 `status` 不能隐藏其他原因。

实现补充：同一运行中断后继续使用原冻结策略；换配置或代码形成新运行，也不能把旧测试重新称为独立证据。`test-use.json` 与已有测试回答用于记录这种重用，不增加人工解锁步骤。跨工作区复制或人工删除记录仍需由实验分析披露历史，程序不声称能证明一个文件从未被外部使用。

报告至少包含：数据与来源组数、全部主分数和分差、逐长度结果、配对区间、最终层集合、实验/测试分别的判断、理论与实测容量、scale、完整与部分配置数、回答/重试/启动次数、输入输出 token、搜索 GPU 墙钟时间、端点评估时间、测试时间，以及失败和截断统计。

如果仅有主实验通过，可陈述“在本次预定分布的独立测试中，自动选出的配置达到质量与容量目标”。若进一步声称搜索方法比其他方法有效，需要静态全层排序、真实前向贪心（束宽 1）和预算匹配随机搜索分别在实验集选配置；所有待比较配置在查看测试结果前共同冻结，再统一测试。随机对照默认按相同请求预算比较，并同时报告启动数和实际时间，不把它冒称为时间完全匹配。

这些方法对照和小规模子空间枚举属于扩展实验，不是主运行的前置程序。若主测试已经被用于改算法，应使用新的测试集开展扩展比较。

## 9. 采用的研究思路与限制

- [KVTuner](https://arxiv.org/html/2502.04420v3)支持研究层敏感度与组合影响，但其量化后端和位宽不同，不能照搬层表或声称已有 FP8 效果保证。
- [动态更新敏感度的贪心量化](https://proceedings.mlr.press/v157/satoki21a.html)启发逐轮重新评估；原工作对象不是本项目 KV Cache，其实验结论不能直接迁移。
- [Successive Halving](https://proceedings.mlr.press/v51/jamieson16.html)与 [Hyperband](https://www.jmlr.org/papers/v18/16-558.html)提供按观测分配评估资源的思路；本文的束搜索、重采样晋级和删层组合是本项目工程设计，没有相应的全局最优或错误淘汰概率保证。
- [RULER 官方仓库](https://github.com/NVIDIA/RULER)提供任务构造参考；本项目自己固定样本来源、长度、评分与划分，并验证当前模型的可解性。

首版不引入 Shapley/BQP、梯度或 Hessian 排名、代理贝叶斯优化框架，以及未经验证缓存读写路径的 KL/NLL 评分。它们可能在后续减少搜索开销，但需要另外证明代理与真实生成质量的关系，不能替代当前目标后端上的独立测试。
