# AutoKV-Skip v3.0 实现计划

日期：2026-09-08。依据：[v3.0 设计文档](DESIGN.zh-CN.md)与[共同语言](../../CONTEXT.md)。阶段 A–F 已完成实现与 CPU 开发验证；阶段 G 的真实数据难度确定和 GPU 实验待目标服务器执行。下文保留各阶段的目标与验收依据，实际操作见[运行手册](RUNBOOK.zh-CN.md)。

交付目标是一个能在现有离线服务器上执行的完整流程：准备合理数据 → 用较小实验集自动选层 → 固定候选 → 用较大测试集验证质量与真实容量 → 导出可从 Linux 设备网页提交的证据。实现结束与主实验取得正结果分开验收。

## 1. 实现范围与复用边界

采用独立的 v3 协议模块和入口，复用已有服务启动、HTTP 请求和底层策略表示。保留 v1/v2 的历史命令、数据与评分语义，不通过修改旧版默认配置冒充 v3.0。

| 现有文件或能力 | v3.0 处理 |
|---|---|
| `autokv/v2_policy.py` 的 `Policy`、端点与容量函数；`selection.py` 的 `Variant`、规范化配置 ID | 复用任意层集合与 P0/P32 表示。若需整理公共位置，只抽取这部分并保留旧导入兼容 |
| `autokv/v2_data.py` 的 `PromptCodec`、`TransformersPromptCodec` | 复用离线 tokenizer/chat 计数接口；不复用旧 45 题生成器与三类数据校验 |
| `autokv/v2_metrics.py` 的 QA 规范化与 F1 基础函数 | 核对边界后复用；v3 自建任务配对评分、16 单元聚合、质量约束和分组 bootstrap |
| `autokv/local_runtime.py`、`commands.py`、`client.py` | 复用本地 vLLM 启停与 HTTP 路径；必要时从已有响应提取 `finish_reason`，不增加额外生成请求 |
| `autokv/v2_runtime.py` | 复用实际 dtype、prefix caching 与 token 一致性验证；另建逐样本增量运行器，不能直接扩大旧 `run_policy` 的输入列表 |
| `autokv/v2_pipeline.py` | 参考实际环境路径读取、输入副本和报告组织；不复用三类评分、组筛选、静态嵌套预算与整个 split 的结果缓存 |
| `scripts/export_v2_results.py` | 复用可用的归档、分片和失败日志处理；提供明确的 v3 导出入口，避免误把 v3 运行报告为 v2 |
| `autokv/cli.py` | 只增加参数解析和分发，不继续把搜索算法和数据生成堆进该文件 |

已新增 `v3_config.py`、`v3_data.py`、`v3_metrics.py`、`v3_search.py`、`v3_runtime.py`、`v3_pipeline.py`。这是按协议职责划分，没有另建插件系统、通用搜索框架、数据库或任务调度服务。

## 2. 配置、数据和接口合同

### 2.1 配置与目录

新增 `configs/v3.0/quality.json`，使用 `schema_version=3`，记录模型/runtime、来源版本、任务结构、长度、开发/实验/测试题数、评分版本、搜索预算及随机种子。

配置需显式包含：`beam_width=2`、`fidelity_samples=[32,96,256]`、总分与任务容差、`min_capacity_ratio=1.5`、重采样次数、`promotion_win_fraction=0.05`。调度默认 `progressive`，备选 `full` 直接评估完整实验集。`max_bf16_layers` 根据模型 KV 结构和容量目标计算；如果用户另设上限，使用二者较小值并在报告中说明。默认不另设墙钟截止；显式请求/时间预算只用于选层与删层，端点与测试开销另外报告，不把预算结束当作证明不存在解。

来源包放在 `data/v3.0/source/`，生成数据放在 `data/v3.0/development/` 和 `data/v3.0/quality/`。这些大文件目录加入 `.gitignore`，只跟踪数据说明、配置和生成代码；实际使用的数据随 `runs/<run_id>/inputs/` 导出。不能因目录被忽略而漏掉真实提示和标准答案。

### 2.2 模块接口

| 模块 | 需要提供的合同 |
|---|---|
| `v3_config` | 加载协议、导出实际参数、计算容量允许的最大层数；不继承旧版 Easy/Hard/Natural 字段要求 |
| `v3_data` | 从本地来源构造开发/正式数据，加载固定 split，返回按 ID 索引和嵌套前缀；无 GPU、无外网依赖 |
| `v3_metrics` | `score_output`、16 单元聚合、相同样本 ID 的配对分差、可行性、排序键、配对重采样 |
| `v3_search` | 只接收实验数据与 `evaluate(policy, split, sample_ids)`，产生层集合与搜索轨迹；不读取测试分数 |
| `v3_runtime` | 对所需 ID 补全缺失回答，维护每次启动与请求记录，返回该前缀的完整评分视图 |
| `v3_pipeline` | 协调端点、选择、测试前写入冻结文件、测试与报告；处理中断恢复和各终局状态 |

保留从源配置、输入副本到结果的对应关系。缓存只复用同一运行语义下的回答；改变模型、数据、scale、生成设置或评分协议时不得静默沿用旧结果。优先使用已有配置标识与输入快照机制，避免新增要求操作者逐项验证的源码树或产物哈希程序。

### 2.3 已实现的操作入口

下列入口已实现；正式 Bash 操作步骤见[运行手册](RUNBOOK.zh-CN.md)。

| 入口 | 执行设备与用途 |
|---|---|
| `python -m scripts.prepare_v3_sources --output data/v3.0/source` | Linux 登录设备下载并整理来源清单；允许指定已有下载文件，不要求服务器联网 |
| `python -m autokv v3-make-data --mode formal --source-dir ... --project-root ...` | 服务器用已有 tokenizer 离线生成正式数据；开发数据改用 `--mode development`，不启动 vLLM |
| `python -m autokv v3-run --development --project-root ... --port 8010` | 一次数据设计所需的 BF16 开发评估，输出难度、错误与截断摘要；不搜索，不读正式测试集 |
| `python -m autokv v3-run --project-root ... --port 8010` | 使用已生成正式数据运行端点、选层、测试与报告；同输入再次执行可续跑 |
| `python -m scripts.export_v3_results --project-root ... --run-id ...` | 导出该运行的成功/失败结果、输入副本和日志，生成网页提交目录 |

实现时补充了 `--hotpot-source` 和 `--input-dir` 处理原站不可达与已有数据导入；镜像分页失败可续传，证据截断会单题重取。实际 chat template 和 tokenizer 身份参与运行输入识别；测试跨运行重用会单独标为 `test_not_independent`，不会改变原选择或伪装成新独立证据。

开发评估是定义数据的一次性工作，不要求每次正式运行重做，不生成必须“通过”才能运行的 pilot 证书。主命令的数据缺失提示应直接给出对应数据准备命令，不跳到旧版 doctor、smoke 或 Git 步骤。

## 3. 分阶段实现

### 阶段 A：配置与离线来源适配

涉及：`configs/v3.0/quality.json`、`autokv/v3_config.py`、`scripts/prepare_v3_sources.py`、`data/v3.0/README.md`、`.gitignore`。

完成固定协议字段、来源版本与许可说明。下载端只准备公开来源文件与清单；服务器适配器读取本地 JSON，不引入完整 RULER/Nemo 运行依赖。源码 ZIP、不存在 `.git`、已有 Git 但无远端都应能工作。

实现时确认实际下载来源含可用的答案别名、文档 ID 和 HotpotQA 支持证据；不能在字段缺失时用问题字符串代替证据。来源文件不足时报告具体缺项，允许补传文件后重试，不回退到旧 12 条自然 QA。

完成证据：用少量原始结构夹具验证两类 QA 适配；配置计算得到当前 `k_max=10`，更改容量目标能得到对应上限；离线加载路径没有隐式下载调用。

### 阶段 B：数据划分、生成和评分

涉及：`autokv/v3_data.py`、`autokv/v3_metrics.py`，以及必要的现有计数/评分基础函数复用。

先统一文档和问题 ID，再分配来源与证据组，最后构造 16 单元。来源分配使用固定种子，先预留开发来源；正式题的 20%/80% 比例由每单元题数保证，不要求原始文档池也严格按相同比例切分。多跳支持文档跨 split 或跨已分配单元时，跳过该来源组合并记录数量。

实现自然背景填充、受保护的证据段和实际 chat token 计数。数据文件保存显式来源索引；同一问题不以四种长度重复计数。数据生成完成后输出题数、来源组数、背景复用和长度分布，帮助核对实际构成。

评分按设计实现：多键配对 F1、多值集合 F1、QA 最佳别名 token F1；总分由四任务和四长度等权组成。完整原始输出始终保存，不能只保存提取后的答案。

完成证据包括：

- 来源重复、共享证据和 HotpotQA 两跳关系不会穿越 split；不同长度不复用同一个问题实例。
- 32/96/256 前缀严格嵌套，各自每单元为 2/6/16 条；完整正式数据每单元为 16/64 条实验/测试题。
- 加长或缩短背景后证据仍完整，模板计数包含生成提示，输出空间没有越过模型上下文上限。
- 错误键值配对、漏值、多报值、别名、空答案、长解释均按预期计分；正常错误答案不会被过滤。
- 总分改善但单任务超出 0.02 的候选仍失败；正负分差方向与 0.01/0.02 的边界正确。
- 共享来源按组重采样；独立组不足时诚实标记区间不可估计，不伪造 1024 个独立样本。

### 阶段 C：逐样本运行与中断复用

涉及：`autokv/v3_runtime.py`，必要时对 `client.py`、现有日志解析和环境路径辅助函数作小范围修改。

先实现与搜索无关的 `evaluate` 合同。运行器读取有效已完成行，只补缺失 ID；逐行写结果并保存每次服务日志。复用已有 vLLM 命令生成和本地进程控制，不扩展为新的多后端平台。

将实际 dtype、prompt token、KV 预算和 prefix caching 检查放在真实请求流程中。容量解析失败影响容量结论，不删除已取得的有效质量回答。记录 `finish_reason` 与输出长度，正常模型输出不重试；暂时性 HTTP 错误最多一次自动重试。

完成证据包括：

- 单策略依次请求 32、96、256 题，实际只发送 256 次成功生成请求；重复请求完整前缀不再启动服务。
- 第 32 题前中断，前 31 条仍被复用；尾行损坏、HTTP 重试与服务启动失败能保存诊断。
- 同层集合不同别名复用；更换输入文本、模型、scale 或输出预算不能混用旧行。
- 实际 dtype 错误、prompt token 不一致、持续请求失败不会被计为正常质量完成。
- 错误答案与输出达到 token 上限的回答只评分一次，不自动替模型“修答”。

这一阶段的模拟客户端能证明续跑逻辑与请求计数，不能证明目标 GPU 的 dtype 或容量。

### 阶段 D：多保真束搜索与反向删层

涉及：`autokv/v3_search.py`、`v3_metrics.py` 中的比较函数，使用阶段 C 的评估接口。

按设计顺序实现 P0 早停、全 32 层扩展、层集合去重、约束排序、32→96→256 调度、宽度 2 的路径保留、首次可行深度停止、全量反向删层与预算终止。对父集合记录相同前缀上的条件边际收益，不能退回一次性静态排名。

晋级数量为目标值，按点估计并列与 bootstrap 排序比例扩充。先复用每个前缀的重采样索引和单题分数，再计算各候选比较，避免重复做大量无关 CPU 工作。实现不需要新的优化器依赖。

完成证据包括：

- P0 可行时不产生单层搜索；第一轮需要搜索时确实考虑所有 32 层。
- 构造条件收益变化的评分场景，验证下一轮会重新考虑先前低排名层；跨原四层组的集合可以产生。
- 两父路径得到同一层集合时不重复请求；全部早期并列时扩大评估，不能按层号只留前两个。
- 从所有已经全量评估的候选中检查可行性，不漏掉因并列扩评而额外完成的可行配置。
- 在完整实验集通过之前不能输出可行配置；反向删除使层数严格下降，并复用已有结果。
- 资源不足或 10 层内未找到时输出有限预算结论；允许存在算法遗漏的协同组合，不把测试夹具包装为全局最优证明。
- 差异清楚的首轮调度应产生 1856 次候选回答；不清楚时允许更多回答，并能从轨迹解释原因。

可用小型确定性评分表枚举其全部集合来检查搜索行为，属于开发测试，绝不成为服务器正式实验的前置枚举程序。

### 阶段 E：主流程、状态与报告

涉及：`autokv/v3_pipeline.py`、`autokv/cli.py`、运行与报告输出。

主流程固定先完成实验集端点与搜索，写出 `selection.json` 后才允许测试生成。测试执行器对 P32/P0/候选去重，搜不到候选不读取测试集；测试失败后仍返回完整负结果，不自动重新选择。

写出完整/部分配置数、回答与启动开销、分层分数、配对区间、理论和实测容量。`complete`、`quality_passed`、`technical_goal_passed` 和原因分别记录，状态定义与设计表一致。报告须同时显示当前候选与安全回退建议，不能把 P32 回退当作目标达标。

完成证据包括：

- 模拟主流程在冻结文件生成前尝试读测试分数会失败；正式搜索只拿到实验数据。
- P0 达标、混合配置达标、测试失败、参照全零、容量缺失、容量不足、无可行解和运行中断均产生对应状态。
- 改写测试得分不会改变已经冻结的层集合；失败后重复启动只续跑原协议缺少的回答，不尝试另一配置。
- 使用完整模拟数据完成数据加载到报告的联调，报告数字能从原始回答重算。
- v1/v2 的原命令入口和历史评分仍可使用，未被新默认配置覆盖。

### 阶段 F：归档与离线运行手册

涉及：`scripts/export_v3_results.py`、`docs/v3.0/RUNBOOK.zh-CN.md`、`README.md`。

归档从实际运行目录收集输入副本、全部成功与未完成回答、搜索轨迹、各次服务日志、CLI 日志和中文报告。支持还没有 `completed-manifest.json`、甚至尚未建立正式运行目录但已有 CLI 失败日志的情况。成功报告单独放在导出目录供网页直接阅读，大包按约 20 MiB 分片。

手册必须给出可以直接按设备顺序执行的 Bash 步骤：

1. Linux 登录设备从 GitHub 网页或 ZIP 下载 v3.0 源码，准备来源包，使用 SCP 传入服务器。
2. 服务器使用独立 `/mnt_d/huangxiaoyuan/autokv-skip-v3.0` 目录、已有 Python/vLLM/模型路径；记录端口，使用 `tmux` 和日志保存命令。
3. 一次性完成数据设计所需的开发评估，固定正式数据；以后直接运行正式主命令或续跑。
4. 在服务器导出完整或失败运行，SCP 回传 Linux 设备。
5. Linux 浏览器进入仓库的 `v3.0` 分支，上传导出目录中的说明、报告、归档或分片，并从网页手动提交。

不能要求服务器或 Linux 设备执行 `git push`，不能要求它们先提交源码才能运行。Git 可用于服务器本地记录，缺少远端、提交号或 `.git` 目录不构成失败。新手册不链接旧多阶段手册作为前置流程。

完成证据：模拟成功与中断运行都能导出/还原，输入与日志不遗漏，分片顺序正确，不包含权重或整个来源语料；文档中的命令和参数与实际 CLI 一致。网页上传操作由用户在 Linux 浏览器执行，不宣称导出器已经替用户发布。

### 阶段 G：目标服务器上的数据确定与正式验证

这一阶段需要真实服务器执行，当前 Windows 工作区不代跑 GPU，也不把 CPU 测试结果当成实验完成。

先用独立 64 条开发样本确定任务难度、提示与 128 token 输出预算是否合适。记录任务层面的调整原因；只按结构和 BF16 可解性调整，不读取正式测试表现来调题，也不筛选 FP8 错题。开发完成后生成并固定新的 256/1024 正式数据。

首次正式运行即测量 P32/P0 的耗时和容量，更新剩余运行成本估计，然后按协议继续搜索与测试。无需额外插入 smoke 或 doctor。实验成功、预算内未找到解以及独立测试失败都保存并回传。

阶段交付是可重算的真实报告。只有目标服务器验证了实际混合 dtype、质量与容量，才把 README 更新为“v3.0 已完成 GPU 验证”；只有主约束达标，才进一步写成“主实验达标”。

## 4. 验证和交付顺序

推荐按 A → B → C → D → E → F 完成实现，开发数据的真实 BF16 评估可在 B/C 可用后进行，正式主运行等待 E/F 完成。文档与默认参数在每个相关阶段同步，不在实现结束后另拼一份与 CLI 不符的手册。

针对协议正确性增加 `tests/test_v3_config.py`、`test_v3_data.py`、`test_v3_metrics.py`、`test_v3_runtime.py`、`test_v3_search.py`、`test_v3_pipeline.py` 和导出测试。每组测试对应上文具体失败模式；不为文件改名、Markdown 措辞或“函数返回自己写入的常量”增加测试。

实现过程中运行所改模块的针对性测试；共享代码有改动或完成联调后运行现有回归与新增测试，例如 `python -m unittest discover -s tests`。服务器无需把这些开发测试再作为正式实验前置步骤。

建议按以下可审查单元提交代码；本计划本身不表示这些提交已经发生：

| 单元 | 完成内容 | 可审查证据 |
|---|---|---|
| 1 | 本轮设计、计划、共同语言与入口说明 | 文档参数、边界、相对链接和历史事实一致 |
| 2 | 来源、配置、生成和评分 | 数据划分、前缀、证据保护与评分边界验证 |
| 3 | 增量运行器 | 逐样本复用、中断保存、真实运行设置传递验证 |
| 4 | 搜索、冻结、测试和报告 | 搜索场景与无测试反馈的联调验证 |
| 5 | 导出、正式手册与回归 | 成功/失败归档、设备步骤、现有命令兼容 |
| 6 | 真实数据协议与运行结果 | 服务器运行后经 Linux 网页提交的原始证据 |

不把算法对照、吞吐基准、校准 scale、梯度代理、Shapley 搜索或更多任务塞入首版必做路径。若需要证明搜索效率优于其他方法，单独按设计文档的共同冻结规则开展对照；其缺席不阻塞主目标验证，其结果也不能倒灌已使用的测试集。

## 5. 交付完成的判断

代码交付完成意味着：能够离线构造新数据，正确执行条件选层与增量推理，将冻结策略送入独立测试，生成不混淆成功与完成的质量/容量报告，并导出成功或失败证据供网页提交。

主实验达标意味着：在合理且预先确定的新任务分布上，冻结候选相对 P32 的四任务等权总分下降不超过 0.01、每任务下降不超过 0.02，且相同 KV 预算的真实容量至少为 `1.5×`。置信区间不足以支持更强结论时照实说明。

没有找到可行层集合、P0 已经足够好、候选测试失败或未能证明非劣性，都是该流程可能得到的结果。实现不得为了预期的“混合配置胜出”改变数据、规则或报告含义。
