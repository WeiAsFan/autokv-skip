# AutoKV-Skip v2.0：质量缺口驱动的混合精度自动选择

状态：设计冻结，待实现

日期：2026-09-02

前置事实：[AutoKV-Skip v1.0 统一项目事实](../v1.0/FACTS.zh-CN.md)

## 1. 正式决策

v2.0 不再固定输出 Auto-4。系统的正式输出改为：**先测量质量缺口，再自动选择满足质量约束且 BF16 层数最少的混合精度策略。**

对 32 层模型定义策略 `P_k`：`k` 层使用 BF16 KV，其余 `32-k` 层使用 FP8 E4M3 KV。

- `P_0` 是全 FP8；它是混合精度策略空间的容量端点，不再作为与“混合精度方法”并列的独立方案。
- `P_32` 是全 BF16；它是质量参考端点。
- `P_2`、`P_4`、`P_8` 是受控搜索预算。
- 最终输出记为 `P*`，它可以是 `P_0`、`P_2`、`P_4`、`P_8` 或 `P_32`。系统不保证一定输出中间混合策略。

这项改变直接吸收 v1.0 的负结果：如果 `P_0` 已与 `P_32` 质量等价，就应选择容量最大的 `P_0`，而不是为了保留项目名称而强行输出 `P_4`。

## 2. 问题定义

在固定模型、运行时、KV Cache 预算、数据和服务参数下，v2.0 回答三个按顺序约束的问题：

1. `P_32` 与 `P_0` 之间是否存在预先定义的质量缺口？
2. 若存在，恢复多少 BF16 层、恢复哪些层，才能把质量拉回允许范围？
3. 被选策略的容量收益与 serving 性能是否足以形成可部署的 Pareto 候选？

质量是硬约束，容量是通过最小化 BF16 层数直接优化的目标，性能是最终部署可行性验证。三者不压成一个可被任意权重操纵的“综合分数”。

## 3. 目标与非目标

### 3.1 目标

- 让策略预算 `k` 由质量证据决定，而不是固定为 4。
- 用更有区分度的合成与自然数据暴露真实量化敏感性，同时保持公平基线。
- 用同预算随机层集合判断收益来自层选择，还是只来自多使用了 BF16 字节。
- 在单张 RTX A6000 和可接受的服务器时长内完成实验。
- 生成能在面试中讲清的决策链：端点差距 → 是否搜索 → 预算/层选择 → 留出集验证 → 容量/性能验证。

### 3.2 非目标

- 不修改 vLLM、FlashInfer 或 CUDA kernel。
- 不做权重量化、激活量化或跨请求在线自适应。
- 不通过关闭合理校准、选择异常 scale 或故意构造乱码来放大 `P_0` 的损失。
- 不追求覆盖完整 RULER 或完整 LongBench 排行榜。
- 不保证混合策略一定优于两个端点；`P_0` 或 `P_32` 都是合法结论。
- 不追溯修改 v1.0 的 EM、Q、数据或结论。

## 4. 公平性不变量

除 `k` 和由选择器确定的 BF16 层集合外，所有策略必须共享：

- 同一模型 revision、tokenizer revision 和 chat template；
- 同一 vLLM/torch/FlashInfer 运行时；
- 同一 attention backend、KV Cache 预算、最大上下文和 generation 参数；
- 同一数据文件、样本顺序和输出上限；
- 同一 KV scale 方案；若运行时支持经过校准的 scale，必须在查看 `P_0` 差距前冻结并用于所有含 FP8 的策略；
- `enable_prefix_caching=False`；
- 同一请求客户端和超时策略。

改变输入数据的目的只能是提高任务区分度，不能是让全 FP8 人为变差。`P_32` 和 `P_0` 必须在完全相同的输入上做逐样本配对比较。

## 5. 三层质量数据

数据总量固定为 45 个正式样本，其中 calibration 27 个、held-out 18 个。正式运行前可以使用不进入报告的 BF16-only 小型 pilot 调整 Hard Synthetic 的任务难度；pilot 最多 9 个请求，并且在任何 `P_0` 结果产生前冻结最终数据。

| 数据层 | 内容 | 正式规模 | Calibration / Held-out | 作用 |
|---|---|---:|---:|---|
| Easy Synthetic | 单针 NIAH，8k/16k/24k 各 2 个固定种子 | 6 | 3 / 3 | 运行正确性与基础长上下文召回 sanity check |
| Hard Synthetic | 3 类 RULER-style 任务 × 8k/16k/24k × 3 个种子 | 27 | 18 / 9 | 主动制造更高但合理的长上下文检索、追踪和聚合压力 |
| Natural | LongBench v1 的 `qasper_e` 与 `hotpotqa_e` 各 6 个固定样本 | 12 | 6 / 6 | 检查合成任务上的结论能否迁移到自然单文档与多文档 QA |
| 合计 | — | 45 | 27 / 18 | 控制总成本并保留独立验证 |

### 5.1 Easy Synthetic

- 继续使用 v1.0 的单针召回形式，但重新生成 v2.0 独立数据，不复用 v1.0 的结果行。
- 上下文目标为 8192、16384、24576 tokens；每个长度使用一个 calibration seed 和一个 held-out seed。
- 它只负责发现运行时错误和明显退化，不作为证明层选择有效的主要证据。

### 5.2 Hard Synthetic

Hard Synthetic 固定使用 8k、16k、24k 三种上下文，不加入 32k，也不在看到结果后追加更长长度。采用三个 RULER-style 任务族：

1. **多键/多值检索**：上下文含多个干扰键值，问题同时查询多个目标；
2. **变量追踪**：经过多次变量绑定或重命名后恢复最终值；
3. **聚合提取**：从长上下文中提取共同词或频率最高的目标集合。

每个任务族在每个长度上使用种子 41、42、43：41 和 42 进入 calibration，43 只进入 held-out。生成器必须根据固定 tokenizer 把 chat template 后的输入填充到目标长度，误差不超过 32 tokens，并为输出预留足够空间。

难度只允许在 BF16-only pilot 中按一个预注册档位上下调整一次。目标不是让 BF16 失败，而是避免 v1.0 那种所有策略都接近满分的天花板效应；pilot 后必须冻结任务参数、种子和数据 hash。

### 5.3 Natural

- 使用 LongBench v1/LongBench-E，而不是上下文可能远超本模型窗口的 LongBench v2。
- 固定两个英文子集：`qasper_e` 代表单文档 QA，`hotpotqa_e` 代表多文档 QA。
- 使用模型实际 tokenizer 过滤 chat template 后超过 24576 tokens 的样本；禁止为迁就窗口而对同一样本采用不同截断。
- 每个子集按稳定 `_id` 哈希分层抽取 6 个样本，3 个 calibration、3 个 held-out；两个 split 不得共享 `_id`、context 或 question。
- 12 个样本只用于自然任务方向性验证，不用于宣称完整 LongBench 排名。

RULER 提供可配置长度和难度的合成任务，且覆盖检索、变量追踪和聚合；LongBench v1 则覆盖自然长文档任务。两者在本设计中互补，避免只靠单一 NIAH 得出结论。

## 6. v2.0 质量指标

v2.0 新增统一的 `task_score ∈ [0,1]`，但不改写 v1.0 产物：

- Easy NIAH：按既有标准化答案命中语义计 0/1；
- Hard Synthetic：使用与任务匹配的答案集合准确率或集合 F1；
- Natural：使用 LongBench 对相应 QA 子集的官方 F1 计算方式；
- Answer NLL 只作为可计算的合成任务诊断指标，不进入跨任务主分数。

分别计算三个层级均值 `S_easy`、`S_hard`、`S_natural`，再对三个层级等权平均：

```text
S_v2(P_k) = (S_easy(P_k) + S_hard(P_k) + S_natural(P_k)) / 3
```

采用层级等权而不是按样本数加权，防止 27 个 Hard Synthetic 样本掩盖 Natural 的变化。所有差值按同一样本配对计算，并报告 bootstrap 95% CI；置信区间用于说明不确定性，不额外触发一串重复门禁。

## 7. 质量缺口与搜索触发

端点缺口定义为：

```text
G_global  = S_v2(P_32)     - S_v2(P_0)
G_easy    = S_easy(P_32)   - S_easy(P_0)
G_hard    = S_hard(P_32)   - S_hard(P_0)
G_natural = S_natural(P_32)- S_natural(P_0)
```

阈值在端点运行前冻结：

- 全局容许缺口 `ε_global = 0.01`；
- Hard 与 Natural 的单层容许缺口 `ε_tier = 0.02`；
- Easy 必须与 BF16 一样通过全部样本。

决策规则：

```text
若 G_global <= 0.01，且 G_hard <= 0.02，且 G_natural <= 0.02，
且 P_0 的 Easy 全部通过：
    不做层搜索，候选输出为 P_0。
否则：
    进入预算与层集合搜索。
```

这是一条简单、预注册、可自动执行的规则。CI 与逐任务结果必须进入报告，但不允许根据 CI 的形状临时改阈值或追加任意样本。

## 8. 条件式预算与层集合搜索

只有第 7 节触发搜索时才执行以下步骤。

### 8.1 两级层排序

1. 把 32 层固定分为 8 个连续四层组；分别运行 8 个 `P_4` 组配置，按相对 `P_0` 的 calibration `S_v2` 恢复量排序。
2. 只保留前 2 个组中的 8 层；分别运行 8 个 `P_1` 单层恢复配置。
3. 按单层恢复量排序，形成一个固定层序列；并列时按层号升序，禁止人工挑层。

这保留 v1.0 coarse-to-fine 的成本优势，但把固定 Auto-4 改成可变预算。

### 8.2 预算候选

从同一层序列构造嵌套候选：

- `P_2`：排名前 2 层保留 BF16；
- `P_4`：排名前 4 层保留 BF16；
- `P_8`：排名前 8 层保留 BF16。

按 `P_2 → P_4 → P_8` 顺序运行 calibration；第一个满足以下全部约束的策略即为候选 `P*`，后续更大预算不再运行：

```text
S_v2(P_k)      >= S_v2(P_32)      - 0.01
S_hard(P_k)    >= S_hard(P_32)    - 0.02
S_natural(P_k) >= S_natural(P_32) - 0.02
P_k 的 Easy 通过数 = P_32 的 Easy 通过数
```

若 `P_8` 仍不满足，输出 `P_32`，并明确结论为“在本次候选预算内没有验证通过的混合精度策略”。不得临时加入 `P_12`、`P_16` 或手工层集合追逐正结果。

### 8.3 Held-out 验证与同预算对照

- 若端点阶段选择 `P_0`，held-out 只运行 `P_32` 与 `P_0`。
- 若搜索选择 `P_2`、`P_4` 或 `P_8`，held-out 运行 `P_32`、`P_0`、所选 `P_k` 以及 3 个固定 seed 的 Random-`k`。
- First-`k`、Last-`k`、Inverted-`k` 和 5 组随机对照不再作为必跑项，避免 v1.0 的实验膨胀。
- held-out 只做一次；不得根据 held-out 结果重新排序层或改预算。

所选策略必须在 held-out 上再次满足第 8.2 节质量约束。若失败，最终安全输出退回 `P_32`，同时保留“calibration 选择未泛化”的负结果。只有所选策略高于 3 个 Random-`k` 的中位数时，才可以说层排序在本次实验中提供了附加价值；否则只能说预算选择有效或证据不足。

## 9. 容量目标

Mistral-7B 的 32 层、8 KV heads、head dimension 128 下，忽略小量元数据时：

```text
bytes_per_token(P_k) = 65536 + 2048 × k
capacity_ratio(P_k vs P_32) = 131072 / (65536 + 2048 × k)
```

| 策略 | 理论容量相对 `P_32` |
|---|---:|
| `P_0` | 2.0000× |
| `P_2` | 1.8824× |
| `P_4` | 1.7778× |
| `P_8` | 1.6000× |
| `P_32` | 1.0000× |

最终报告同时给出理论值和 vLLM 实测 token capacity。容量不需要对每个搜索中间配置重复三次：端点与最终候选各记录一次真实启动值即可。

## 10. 性能验证边界

性能是选择 `P*` 后的后续阶段，不属于当前阶段 2–4 执行计划，但设计约束现在冻结：

- 必须设置 `enable_prefix_caching=False`；
- 只比较 `P_32`、`P_0` 和最终 `P*`；若 `P*=P_0` 或 `P*=P_32`，去重后只剩两个配置；
- 每个配置一次 server 启动、一次不计入结果的 warm-up，再运行固定重复；
- 按相同 input/output、并发和请求数比较 throughput、TTFT、TPOT、ITL；
- 容量收益不能替代延迟或吞吐证据，性能也不能覆盖质量约束；
- 性能 SLO 和主场景必须在运行前另行冻结。

v2.0 不再把所有质量对照都跑性能；Random-`k` 只证明层选择，不承担 serving benchmark。

## 11. 必要且精简的证据控制

v2.0 只保留四类必要控制：

1. **源码与数据身份**：一个 run manifest 记录公开 Git commit、源码树 hash、配置 hash、数据 hash、模型/runtime 身份。
2. **内嵌启动检查**：首次 `P_32` 与 `P_0` calibration 的第一条请求同时充当 smoke；检查响应可解析、dtype 日志正确、prefix caching 关闭，不再另跑双 smoke。
3. **策略级完整性**：每个策略只有一个状态，满足预期行数、0 失败、JSONL 可解析并记录一个结果 hash 才算完成；resume 只在策略粒度工作。
4. **留出集隔离**：calibration 与 held-out 的 ID/hash 在运行前冻结；held-out 结果不得反馈到排序和预算。

明确删除以下 v1.0 式重复控制：独立 doctor/lock/dry-run/双 smoke 串联、同一命令在多个状态文件重复哈希、每个派生 CSV/SVG 单独设门禁、为同一 server 反复做等价正确性启动。保留一份原始 server log、一份策略 manifest 和最终归档清单即可。

## 12. 成功与失败解释

| 结果 | 正确解释 |
|---|---|
| `P_0` 通过质量约束 | 全 FP8 是本数据/运行时下最优容量端点；自动选择器正确停止，无需混合 |
| 中间 `P_k` 通过且优于随机中位数 | 质量缺口存在，预算和层选择均得到支持 |
| 中间 `P_k` 通过但不优于随机中位数 | 混合预算有价值，当前层排序未证明有额外价值 |
| 只有 `P_32` 通过 | 当前 FP8 路径无法在候选预算内满足质量约束；诚实回退 BF16 |
| Calibration 通过、held-out 失败 | 选择过拟合，输出回退 `P_32`，不得换数据重选 |
| 三层数据仍无缺口 | 得到边界清楚的负结果，不继续人为加难或改变 scale 追逐 Auto 策略 |
