# AutoKV-Skip v4.0 实现计划

日期：2026-09-14。分支：`v4.0`，基于 `abc3efc9fe7bb1deff48e184270e4528457197ad`。

状态：功能阶段 A–F 已实现，阶段 G 的 CPU 与真实 tokenizer 布局验证已完成；GPU 数据构造与主实验待在服务器运行。实施以[设计文档](DESIGN.zh-CN.md)和[共同语言](../../CONTEXT.md)为准；验证范围见[验证记录](VALIDATION.zh-CN.md)，操作见[离线运行手册](RUNBOOK.zh-CN.md)。下文保留原阶段合同，标明实际完成边界。

交付链条：有限难度扫描 → 两批新数据确认 BF16 可解与 FP8 强缺口 → 冻结数据规则 → 新实验集/测试集 → v3.0 自动选层流程 → 离线导出与 Linux 网页提交。

## 1. 代码审查结论与复用范围

v3.0 已具备逐样本运行器、束搜索、反向删层、候选冻结与独立测试。它不直接支持本版的新数据结构，不能仅将新 JSONL 放入旧目录后声称复用了完整协议。

| 现有代码 | 已核对的限制 | v4.0 实施方向 |
|---|---|---|
| `autokv/v3_config.py` | `TASKS` 固定四任务，要求四长度；`cells`、`epsilons` 依赖常量 | 增加显式任务/长度配置访问；v3 配置校验保持原规则，v4 正式配置支持选中的一个任务与长度 |
| `autokv/v3_data.py` | 生成和校验依赖旧四任务、16 单元及来源三划分 | 复用来源规范化、离线 tokenizer、背景适配能力；新建两类生成器与四阶段数据合同，不将新题伪装成旧任务 |
| `autokv/v3_metrics.py` | 评分只接受旧任务，聚合和有效参照检查写死四任务/四长度 | 为新短答案增加独立评分；聚合、配对和重采样按显式协议工作，保持 v3 默认行为 |
| `autokv/v3_runtime.py` | 新回答与缓存重算直接调用旧 scorer；预算只计 `search`；统计阶段列表固定 | 注入或明确分发评分函数；复用原运行器，纳入发现/确认阶段计数，不漏计新阶段或改变旧搜索预算语义 |
| `autokv/v3_search.py` | 核心算法可复用，但直接调用固定任务的聚合函数 | 传递显式协议完成数据适配；保留扩展、排序、晋级、首个可行深度、删层与预算退出逻辑 |
| `autokv/v3_pipeline.py` | 路径、运行前缀、schema、报告表头固定 v3；开发模式只跑 P32；测试使用记录只扫描 `v3-*` | 新构造协调器复用正式执行流程；最小参数化版本/路径/表头及输入快照，测试重用记录覆盖 v3/v4 |
| `scripts/export_v3_results.py` | 只识别 v3 目录、配置与报告 | 复用归档/20 MiB 分片逻辑，提供明确 v4 导出入口，带全构造与正式实验上下文 |
| `autokv/cli.py` | v3 入口已有，旧命令包含历史 doctor/smoke 路径 | 新入口只做参数解析和调度，不调用历史前置程序，也不将新逻辑堆进 CLI |

优先让 v3 的公共函数接收实际协议，默认保持 v3 行为；不要全局修改 `TASKS`，不要复制题目满足旧断言，不要给 v4 复制一套束搜索。新生成器、构造控制与报告确属本版职责，可以使用小型 v4 模块，不建立插件框架、数据库或通用优化平台。

## 2. 参数和模块合同

### 2.1 配置

计划新增 `configs/v4.0/quality.json`，`schema_version=4`。其中构造需求与最终质量阈值放在不同字段，不能复用同一个 epsilon。

| 字段 | 默认值 |
|---|---|
| `construction.min_bf16_score` | `0.80` |
| `construction.min_fp8_gap` | `0.10`；可在构造前改为 `0.20` |
| `construction.tasks` | `single_lookup`、`two_hop_lookup` |
| `construction.target_lengths` | `[8192, 16384, 24576]` |
| `construction.record_counts` | `[16, 64, 128, 256]` |
| `construction.discovery_per_condition` | `64` |
| `construction.max_confirmation_conditions` | `2` |
| `construction.confirmation_batches` | `2` |
| `construction.confirmation_per_batch` | `512` |
| `data.experiment_samples` / `data.test_samples` | `512` / `4096` |
| `data.seed` / `data.max_tokens` | `20260914` / `32` |
| `data.input_tolerance_tokens` | `128` |
| `search.beam_width` / `search.schedule` | `2` / `progressive` |
| `search.fidelity_samples` | `[32, 96, 512]` |
| `search.promotion_win_fraction` | `0.05` |
| `search.max_requests` / `search.max_seconds` | `24576` / `null` |
| `thresholds.epsilon_global` / `epsilon_task` | `0.01` / `0.02` |
| `thresholds.min_capacity_ratio` | `1.5` |
| `scoring.version` | `autokv-v4-short-code-v1` |
| `scoring.bootstrap_samples` | `2000` |

发现阶段的多条件配置与冻结后的正式数据协议要区分。正式协议明确记入所选任务、唯一长度、记录量、来源划分和构造运行，提供 v3 搜索所需的 `tasks`、`lengths`、`cells`、`experiment_size`、`fidelities`、`epsilons`、`max_layers`、`profile()` 等接口。

与 v3 共用函数时显式传入正式协议，不能通过覆盖模块常量改变进程中另一版本的评分。模型/runtime 设置沿用设计文档，参数变化进入实际输入与运行身份，缓存不跨规则混用。

### 2.2 职责划分

| 计划新增或适配的模块 | 合同 |
|---|---|
| `autokv/v4_config.py` | 读取构造配置、验证直接影响实验的参数关系，产出冻结规则对应的正式协议 |
| `autokv/v4_data.py` | 四阶段来源分配、基础实例生成、证据保护、实际长度适配、新数据加载与必要结构检查 |
| `autokv/v4_metrics.py` | 六位代码评分、按条件/确认批汇总、构造判据与 v4 结果字段；复用现有配对和统计能力 |
| `autokv/v4_construction.py` | 有限网格、确认对象排序、两批新样本、规则冻结与未找到结论；不接触层搜索或测试成绩 |
| `autokv/v4_pipeline.py` | 协调构造与正式流程、输入快照和 v4 报告；正式选层调用既有算法 |
| `autokv/v3_metrics.py`、`v3_runtime.py`、`v3_search.py`、`v3_pipeline.py` | 仅作上述复用所需的显式协议/评分/路径适配，保持历史默认行为 |
| `scripts/export_v4_results.py` | 导出一个运行的所有阶段及失败日志，生成 v4 网页提交目录 |

若构造统计和正式评分放在同一个小模块更清晰，可以合并相邻职责；不得改变设计规定的样本隔离、阈值或选择顺序。

### 2.3 计划中的用户入口

以下入口已实现，完整设备命令及日志保存方式见运行手册。

| 入口 | 行为 |
|---|---|
| `python -m autokv v4-run --project-root ... --source-dir ... --port 8010` | 默认执行构造，成功后自动生成正式数据并接续 v3 选层流程；失败则给出构造结果并导出所需信息 |
| `python -m autokv v4-run --construction-only ...` | 只完成发现、确认和规则冻结，用于查看构造结果与实际成本；不是默认主流程前必须手动执行的步骤 |
| `python -m autokv v4-run --run-id v4-... ...` | 续跑同一轮或将仅构造运行接续到正式实验，不重新抽样、复测正常错误答案或重选已冻结层集合 |
| `python -m scripts.export_v4_results --project-root ... --run-id v4-...` | 导出成功、负结果、中断或失败；即使主运行目录未完整建立，也保留 CLI 日志 |

来源准备优先复用已存在的 `scripts.prepare_v3_sources` 和离线来源包，无需另写下载器。新运行有新 ID；给出旧 `run-id` 时使用保存的输入，当前配置变化不能静默覆盖该轮。命令默认输出可复制的运行 ID、当前阶段和报告路径。

运行 ID 在构造开始时建立，依据当时已知的配置、来源、模型与代码输入，不依赖尚未选出的规则或尚未生成的正式数据。规则和正式数据的标识随后写入同一运行；`--construction-only` 只是本次执行的停止位置，不改变科学输入或生成另一个运行身份。显式 `--run-id` 接续时不能因这个标志消失而重复构造。

## 3. 实施阶段 A：配置与共用协议适配

**已实现并通过 CPU 验证。** 建立 v4 配置与冻结正式协议，消除共用路径上的固定任务/长度假设，同时保持 v3 配置本身的四任务要求。

需要逐一适配 `aggregate`、`reference_valid`、`comparison`、`resampled_summaries`、`promote`、搜索中父集合汇总与报告表头。参数应由调用链显式传递，不能只改最终报告而让搜索内部仍按旧任务汇总。

完成证据：

- `Δ_0=0.10` 不满足构造阈值；`Δ_0>0.10` 才满足。改为 `0.20` 后，介于两者的差距不能通过。
- `Q_B=0.80` 满足可解性；两批中的任一批不满足，则不能被合并平均“救回”。
- 构造阈值调整不改变 `0.01/0.02` 选层容差或容量上限；当前 `k_max=10`。
- 旧 v3 配置与样本仍产生原评分、排序和容量结果；新协议允许一个任务、一个长度，不制造缺失任务错误。

本阶段不增加“开发报告哈希正确”“Git 工作区干净”或“版本字符串精确匹配”等实验外检查。

## 4. 实施阶段 B：来源、生成器与评分

**已实现并通过 CPU 与真实 tokenizer 布局验证。** 从本地来源文件复用文档规范化，生成四个阶段的背景池。用新生成器创建映射和查询，不复用旧多值枚举结构。

将完整证据与可裁剪背景分开，按实际 tokenizer/chat template 调整长度。双事实间距在最终文本的 token 位置上计算，不能只按字符下标假定满足。保存最终证据位置、题内映射、基础实例 ID 和所用背景 ID。

发现集先生成完整条件列表；确认对象选定后生成新的两个批次；只有冻结规则后才生成正式实验/测试数据。一个正式实例只产生一道题，不复制为多个长度变体增加题数。

完成证据：

- 随机生成的真值可从保存映射直接计算；目标唯一、干扰映射无冲突，两事实题确实需要关联两条事实。
- 背景裁剪不能删除证据；实际长度与输出空间满足模型约束。结构上放不下的条件有明确记录，不发送模型请求。
- 发现、确认两个批次、实验、测试不共享基础实例；四个阶段的背景来源组隔离。
- 正确裸代码、含唯一正确代码的短句/JSON、重复正确代码、多个不同代码、错误代码、嵌在更长数字中的六位串、空输出均按约定评分。
- 更换长度、记录量或背景不会丢失来源与基本世界对应关系；不会按模型对错过滤生成题。

新增评分测试应验证这些语义边界，避免只复述正则表达式。将大来源、生成数据加入 `.gitignore`，跟踪生成代码、配置、数据说明与许可，实际使用题目由运行归档保存。

## 5. 实施阶段 C：两端构造运行与续跑

**已实现并通过模拟服务联调。** 为现有逐样本运行器提供新 scorer，并同时用于新回答与缓存重算。新阶段使用 `discovery`、`confirmation` 及固定 `batch_id`，不在同一目录中覆盖上一条件的样本。

把所有发现条件的题合并成一次 P32 评估和一次 P0 评估，结果再按 `condition_id` 汇总。确认阶段同理，将两个条件、两个批次合并按精度执行；每批的判据分别计算。服务启动重试属于异常开销，不计入理想两次启动的承诺。

实现设计中的排序、最多两个确认对象、两批均达标及最终规则排序。条件清单在运行前确定，确认题在选定条件后用独立种子生成；恢复执行直接读取保存的数据，不重置随机序列。

完成证据：

- 用模拟响应驱动从不同发现结果选择对应条件、进入新确认批，成功后写出完整冻结规则。
- 某批 BF16 不足、某批 FP8 缺口不足、两批方向冲突和全部条件未成功均能正常完成报告；不创建正式选层请求。
- 不完整 HTTP 请求不会当作零分；正常错误答案只运行一次。
- 中途退出后只补缺失样本；既有确认失败不会因重启变成新一轮抽样。
- 统计包含发现/确认的请求、重试、启动与秒数，合计不会漏掉 v3 原枚举列表之外的阶段。
- 内部输入识别可阻止不同题、不同阈值或生成设置的旧回答混用，不要求用户手工检查摘要。

模拟只能验证逻辑，不能作为找到量化敏感数据的证据。

## 6. 实施阶段 D：冻结规则后接续 v3.0 正式流程

**已实现并通过模拟服务联调。** 由冻结规则构造新的 `512/4096` 数据，生成一个任务、一个长度的正式协议。保持 `v3_search.search` 的算法主体，打通新 scorer、聚合和嵌套前缀。

正式流程中的顺序不变：两端 → P0 可行性 → 必要时束搜索 → 完整实验集反向删层 → 写出 `selection.json` → 独立测试。没有可行候选时正常终止；不新增随机补充搜索或强测失败候选。

最小适配正式运行快照、报告路径和 schema，使 v4 的输入目录、数据规则、构造证据被正确保存。旧 `--development` BF16-only 入口保留其历史含义，不让新流程依赖它。

完成证据：

- 构造未成功不会进入搜索；构造成功不会直接把某个层表写成答案，搜索只读新实验集。
- P0 在新实验集意外满足最终容差时保持 P0 早停，报告不一致而不是重新抽题。
- `32→96→512` 只需 512 次成功生成，复用前缀；所有正式候选用同一顺序。
- 非连续层组合、条件边际收益、软晋级和删层行为沿用原算法；不因单任务适配改变排序目标。
- 部分评估未完成不能冒充实验可行，预算耗尽后不重置计数；已有完整可行候选可冻结。
- 冻结文件先于测试请求；测试失败不换层。没有候选时不伪造独立测试。

对共用代码运行相关 v3 搜索、指标、运行器和流水线回归。仅在这些共用修改影响到其他版本时扩展对应回归范围，不重跑与改动无关的昂贵实验。

## 7. 实施阶段 E：结果字段、统计与报告

**已实现并通过 CPU 验证。** 分开生成构造报告与正式质量/容量报告，主 manifest 汇总两者。按设计区分 `construction_passed`、`technical_goal_passed`、`data_conditions_reproduced`、`recovery_demonstrated` 与 `complete`。

构造报告覆盖全部条件、两批确认分数/区间、BF16 错误类型与截断情况、所选规则或未找到原因。正式报告沿用原端点/候选分数、质量容差和真实容量，并补充测试中是否复现了 `0.80/0.10` 数据条件。未运行测试时相关结果为 `null`，不能以 0 代替缺失证据。

配对区间沿用现有样本/来源组重采样，bootstrap 重复数默认 2000。BF16 正确率可以用不新增依赖的二项比例区间；发现集、各确认批和测试分别报告，不能把选择用过的数据并入测试以缩小区间。若全配对分差相同使 bootstrap 退化，明确标记其不能给出可靠总体不确定性，不将 `[0,0]` 写成精确非劣性证明。区间不产生额外程序准入步骤。

完成证据：

- 主目标达标但测试 FP8 缺口仅 `0.08` 时，仍能正确显示强恢复场景没有复现。
- 原始答案错误、无效输出、重复与截断统计可核对，报告分母保持完整。
- 真实容量缺失或冲突时保留质量结果并标为未验证，不用理论 `1.5×` 替代。
- 新旧版本的测试使用记录均被读取，换 `v4-` 前缀不能绕过已有同题使用记录；同运行续跑仍可继续。
- 报告正确显示新任务名、题数、阈值和版本，不残留“固定四任务”“1280 题”或 v3 标题。

## 8. 实施阶段 F：导出、入口与运行手册

**已实现，手册已编写。** 接入 `v4-run` 与导出入口，入口保持少量参数。首次默认命令完成整条链，不要求用户依次运行独立 doctor、smoke、发布或人工校验程序。

导出内容包括实际源码/配置/规则、发现与确认样本及原始回答、正式样本及回答、搜索轨迹、服务/CLI 失败日志。20 MiB 分片沿用已有方式，避免将模型权重、完整缓存、`.git` 或整个未使用来源库打包。构造未找到也必须有可从网页提交的结果目录。

功能完成后编写 `docs/v4.0/RUNBOOK.zh-CN.md`，明确两台 Linux 设备的命令归属：

1. Linux 登录设备下载 `v4.0` 源码 ZIP 和缺少的来源，允许复用已有离线包，经 SCP 传入服务器。
2. 服务器使用 `/mnt_d/huangxiaoyuan/autokv-skip-v4.0` 与已有模型/虚拟环境运行，保存 CLI 日志与退出码。默认主命令自动从构造衔接到正式实验。
3. 无论成功、未找到还是中断，导出已有结果，经 SCP 回传 Linux 登录设备。
4. Linux 浏览器进入 GitHub 的 `v4.0` 分支，手动上传并提交；两台设备都不执行 GitHub 推送。
