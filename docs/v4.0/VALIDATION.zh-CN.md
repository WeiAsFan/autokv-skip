# v4.0 实现验证记录

日期：2026-09-14。分支：`v4.0`。已完成本地功能验证和相关历史回归，以及真实 Mistral tokenizer 的布局检查。本记录没有 BF16/FP8 模型成绩或真实 KV 容量测量；数据是否满足构造目标、层搜索能否恢复质量，需要按[运行手册](RUNBOOK.zh-CN.md)在目标服务器验证。

## 1. CPU 功能与回归

本地环境为 Windows、Python 3.11.9。验证采用标准库 `unittest`，模型请求由模拟服务代替；端点执行、逐题持久化、缓存计分、束搜索、删层、冻结、报告和归档均调用生产代码。

| 范围 | 数量 | 覆盖内容 |
|---|---:|---|
| `test_v4_metrics.py`、`test_v4_data.py`、`test_v4_pipeline.py` | 36 | 新协议、评分、生成、两批确认、正式流程、续跑和导出 |
| 既有 `test_v3*.py` | 41 | 原四任务评分/数据、搜索排序/软晋级/删层、运行器和报告/导出回归 |
| `test_v2_data.py`、`test_cli.py` | 18 | 共用 tokenizer 扩展和 CLI 分发对旧流程的影响 |
| 合计 | 95 | 全部通过 |

关键验证结果：

- `Q_B=0.80` 通过可解性边界，`Δ₀=0.10` 不能通过严格缺口边界；改为 `0.20` 不改变最终 `0.01/0.02` 容差或容量允许的层数。
- 短句/JSON 中的唯一正确六位代码、重复正确代码、多个不同代码、长数字/字母数字标识和空输出按预定语义计分。读取缓存时也使用同一新 scorer 重算。
- 映射真值可直接求解，单值任务满足共享词干扰条件，双事实需要关联两条记录。基础映射换查询或排列顺序仍识别为同一世界；四阶段与确认两批不复用实例。
- 背景分配为四阶段，文档规范化与重复合并继续复用既有实现。生成中断只补固定身份的缺失题，不换种子重新抽样。
- 多个条件按精度合并运行：发现两次启动、确认两次启动；结构不可构造条件不启动服务。任一确认批失败不能被合并分数救回。
- 完整模拟流程能选择非连续的 `[1,5]` 混合层，并按新单任务/单长度协议验证；这只证明调用链和算法行为，不是模型效果。
- 构造未找到不选层，P0 在新实验集达标时保留早停，搜索预算耗尽不强测失败候选。测试前冻结，测试中断/失败不重新选层。
- 显式运行 ID 接续保存的配置，不受当前配置文件覆盖；只做构造后可以直接进入正式阶段。正常错误答案不重试，HTTP 失败不计为零分，逐题续跑只补缺失回答。
- 测试质量达标但强 FP8 缺口未复现时，`technical_goal_passed` 和 `recovery_demonstrated` 正确区分。真实容量缺失、测试重用、报告失败均不能留下错误的恢复成功标记。
- 没有 `.git`、只有 CLI 失败日志、构造负结果、部分回答和分片归档均可导出；完整未使用语料和模型权重不进入结果归档。

复现 CPU 回归的命令如下，仅用于本地开发验证，不是服务器正式实验的前置程序：

```bash
python -m unittest discover -s tests -p 'test_v4*.py'
python -m unittest discover -s tests -p 'test_v3*.py'
python -m unittest tests.test_v2_data tests.test_cli
```

本次 Windows 执行时，测试进程将 `tempfile.tempdir` 设为系统临时目录的解析后路径，避免 `ADMINI~1` 与完整用户名路径混用，并给子进程设置 `PYTHONUTF8=1`，避免父子进程字符集不一致。这些是本地测试环境适配，没有修改生产文件路径逻辑或要求服务器设置这些选项。

## 2. 真实 tokenizer 布局验证

使用配置指定的 Mistral-7B-Instruct-v0.3 revision `c170c708c41dac9275d15a8fff4eca08d52bab71` 的 tokenizer 文件，调用生产 `TransformersPromptCodec` 和 `generate_sample`。本地临时依赖为 Transformers 4.57.3、tokenizers 0.22.2；只加载 tokenizer，不下载模型权重、不启动 GPU，也不要求服务器更换依赖版本。

验证覆盖默认全部 24 个条件，每条件生成 `discovery` 阶段、`batch_id=discovery`、索引 `0/1/2` 的三个实例，共 72 个尝试。自然背景使用测试夹具，以便检查长度、完整记录与 token 位置；它们不作为构造实验数据。详细布局结果见 [TOKENIZER-CHECK.json](TOKENIZER-CHECK.json)。

| 结果 | 观察 |
|---|---|
| 合法布局 | 69 个，全部满足目标长度 ±128 tokens，完整记录保留 |
| 双事实间距 | 合法布局的最小间距约为输入 token 数的 `0.407`，超过三分之一 |
| 结构不可构造 | `two_hop_lookup / 8192 / 256` 的三个实例，完整记录、问题和模板至少需 15,435 tokens |
| 输出空间 | 所有合法布局均给 32 tokens 输出预留空间，未超过 32,768 上下文上限 |

没有据这三个不可构造实例改变既定网格；正式运行仍记录该条件并依实际 tokenizer 判断。此检查不衡量 BF16 可解性，也不提供 FP8 退化或恢复证据。

已核对 `v4-run` 与导出命令的帮助、文档入口和相对链接，执行 Python 编译检查及 Git 差异检查。共用搜索的变化限于显式传递任务/长度协议，没有复制优化器或加入随机补充搜索。

真实服务器下一步直接执行完整 `v4-run`。两批确认均通过才可称数据构造完成；有效独立测试质量与实际容量同时通过才可称主目标达标；正式测试复现强缺口且混合层恢复成功才可称强恢复场景成立。CPU 模拟通过与退出码 0 不能代替这些结论。
