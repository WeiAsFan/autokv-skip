# AutoKV-Skip v4.0 设计文档

日期：2026-09-14。分支：`v4.0`，从包含 v3.0 运行结果的 `abc3efc9fe7bb1deff48e184270e4528457197ad` 建立。

状态：设计与实现计划对应的代码已实现，已完成 CPU 与真实 tokenizer 布局验证，见[验证记录](VALIDATION.zh-CN.md)；尚未进行 v4.0 GPU 实验。操作见[离线运行手册](RUNBOOK.zh-CN.md)，术语及设备边界见[共同语言](../../CONTEXT.md)。

## 1. 版本目标

v4.0 的主流程是：

> 通过调整任务难度并实测，构造 BF16 可解且全 FP8 有明显恢复需求的数据分布；冻结构造规则并生成新的实验集、测试集；然后执行 v3.0 的 AutoKV-Skip 端点判断、束搜索、反向删层、冻结候选和独立测试流程。

本版主要解决数据适配问题。保留 v3.0 的选层算法，不能由数据准入推断束搜索已经有效，也不预设一定存在满足质量与容量要求的混合配置。构造成功与自动选层成功分别报告。

模型权重保持 BF16；只对 KV Cache 选择 BF16/FP8 E4M3。技术主目标仍是在独立测试中满足质量下降约束，同时在相同 KV 显存预算下取得至少 `1.5×` 实测容量。吞吐加速、全局最优或论文级算法创新不属于主验收。

本版默认只选择一个任务族与一个难度条件进入正式实验，以回答限定分布上的可行性问题。不会将其结果称为原 v3.0 四任务协议或官方 RULER 成绩。

## 2. 为什么先解决数据

已归档的 [v3.0 运行报告](../../results/v3-20260909T062152.212632Z/v3-a502366f75cc8179-QUALITY-v3.zh-CN.md)来自运行 `v3-a502366f75cc8179`：

| 观察 | v3.0 结果 | 对 v4.0 的含义 |
|---|---|---|
| 实验集端点总分 | BF16 `0.450319`，P0 `0.459953` | 实验集没有提供进入混合搜索的质量缺口 |
| 实际搜索 | `search.requests=0`，选择 `P0=[]` | 本次没有检验束搜索的真实恢复效果 |
| 测试总分 | BF16 `0.500070`，P0 `0.491402`，下降约 `0.008668` | 缺口较小；其配对 95% 区间约为 `[-0.0010, 0.0185]` |
| 多键检索测试 | BF16 `0.710938`，P0 `0.678646`，下降约 `0.032292` | 存在值得调查的线索，但没有达到本版要求的 10 个百分点强差距 |
| 多值检索 BF16 测试 | `0.123215` | BF16 本身难以可靠完成该任务，不能只增加 FP8 难度 |
| 实测容量 | P32 `131072`，P0 `262144` KV tokens | 真实容量达到 `2.0×`；质量问题与容量结果须分别解释 |

v3.0 的状态为 `test_quality_failed`，主目标未达标；多键检索的测试下降超过其单任务容差。原始输入、回答和日志随[结果归档](../../results/v3-20260909T062152.212632Z/README.zh-CN.md)保存。此前对原始输出的分析还观察到多值检索枚举背景、重复生成和输出截断，因此本版先采用明确、短输出的任务。

`0.01` 的差距是否属于采样波动取决于配对结果和样本量，不是固定的统计误差界限。本版采用 `0.10`，是要求一个足够大的恢复对象；仍使用全新确认样本和区间来评估其可靠性。

## 3. 两个质量阈值必须分开

记 `Q_B` 为全 BF16 正确率，`Q_0` 为全 FP8 正确率，`Q_S` 为保留层集合 S 的正确率：

```text
Δ_0 = Q_B - Q_0
Δ_S = Q_B - Q_S
```

| 判据 | 默认值 | 用途 |
|---|---|---|
| `construction.min_bf16_score` | `0.80`，使用 `Q_B >= 0.80` | 判断短答案任务在 BF16 下可解；接近满分也可以 |
| `construction.min_fp8_gap` | `0.10`，使用 `Δ_0 > 0.10` | 判断全 FP8 是否有明显恢复需求 |
| `thresholds.epsilon_global` | `0.01`，使用 `Δ_S <= 0.01` | 沿用 v3.0 的最终总分质量容差 |
| `thresholds.epsilon_task` | `0.02` | 沿用任务级容差；本版只有一个主任务，总分约束更严格 |
| `thresholds.min_capacity_ratio` | `1.5` | 相同 KV 显存预算的实测容量倍率 |

用户提出的 `0.10/0.20` 均是绝对正确率差，即 10/20 个百分点，不是相对百分比。首版选 `0.10` 作为默认下限；若希望要求 20 个百分点，在构造运行开始前将同一字段设为 `0.20`。不得因为某次结果未达到 `0.20` 而在原运行中降到 `0.10`，更不能降回 `0.01`。

等于 `0.10` 不满足严格的 `>` 条件；不能先四舍五入再判断。最终混合配置仍必须恢复到 `0.01` 以内，不能把它的容差一并放宽到 `0.10`。例如 BF16 `0.90`、P0 `0.75`、S `0.895` 可满足这些质量点判据，S `0.85` 则不能。

数据准入依据两批新确认样本各自的点估计，具体流程见第 5 节。配对区间用于说明证据强度，不增加一个必须取得统计证书才能执行选层的程序。若区间跨越 `0.10`，报告应写明“确认批点估计达到强差距要求，其分布差距下界尚未被证实超过阈值”。

## 5. 数据构造阶段

### 5.1 两个任务族

采用 RULER 的可控检索思路，并参考 BABILong 将简单事实放入长背景的方式，自行生成可直接计算真值的任务，不运行其完整评测框架。[RULER 参数](https://raw.githubusercontent.com/NVIDIA/RULER/main/scripts/synthetic.yaml)、[RULER 提示](https://raw.githubusercontent.com/NVIDIA/RULER/main/scripts/data/synthetic/constants.py)、[BABILong 官方仓库](https://github.com/booydar/babilong)

**`single_lookup`：相似记录中的单值精确检索。** 每题独立生成键值表，查询一个对象的六位代码。键由两个自然词组成；完整键唯一，至少一半干扰键与目标共享其中一个词，所查代码只出现在目标记录中。

```text
Each record gives a subject and its six-digit access code.
Use only the access_code field of the matching subject.

Record: subject=blue heron; access_code=482731.
Record: subject=blue otter; access_code=927415.
...其他记录与背景...
Record: subject=green heron; access_code=163824.

What is the access_code for blue heron?
Return only the six-digit code.
```

**`two_hop_lookup`：两条事实的关联查询。** 每题独立生成“案件→储物柜→六位代码”的无冲突映射，查询一个案件的最终代码，不要求输出中间过程。

```text
Case C42 uses locker L17.
...其他记录与背景...
Locker L17 has access code 482731.

What is the access code for the locker used by case C42?
Return only the six-digit code.
```

两类任务的所有代码在题内唯一；案件、柜子和键的映射不歧义。生成器保存完整映射、目标对象与真值。这里控制的是准确检索和记忆负担，不能预先断言干扰越多或上下文越长，FP8 损失就越大。

背景复用现有离线 SQuAD/Hotpot 来源包中的自然文本，明确区分背景与待查记录。目标事实散布在全文中，不组成总在最后的便利答案表。单事实位置按预定均匀分布抽样；双事实位置随机且相距至少实际输入的三分之一，证据先后顺序可以互换。

### 5.2 用有限难度网格进行实测

本版以一个小型、完整的网格实现难度调整，逐条件真实比较，不假定难度或量化损失单调，也不使用二分法跳过中间现象：

| 轴 | 默认取值 |
|---|---|
| 任务 | `single_lookup`、`two_hop_lookup` |
| 实际输入长度 | `8192`、`16384`、`24576` tokens，容差 `128` |
| `record_count` | `16`、`64`、`128`、`256` |
| 条件总数 | `2×3×4=24` |
| 每条件发现样本 | `64` 个不同基础实例 |
| 确认条件数 | 最多 `2` 个 |
| 每条件确认样本 | 两批全新实例，每批 `512` 个 |

对于 `single_lookup`，`record_count` 是包含目标的记录总数；对于 `two_hop_lookup`，是案件映射数量，并有等量柜子代码映射。因此双事实任务有 `2×record_count` 条记录。两者的含义固定，不在报告中混用。

保持语义任务与输出形式不变，主要改变记录量与上下文长度。记录无法在某个长度内完整容纳时，将该条件记为结构上不可构造，并记录所需 token 数；不能裁掉证据或循环生成直到某个模型更容易失败。只缩放非证据背景，实际输入计数包含 chat template 与生成提示，始终预留输出空间。

这是本轮预先限定的构造范围；没有找到不排除其他任务、长度、记录量或量化方式。改变词表、提示、相似度规则或网格范围属于新的构造运行，需要保存新参数；不在已冻结的正式实验中继续调整。

### 5.3 发现、确认与规则冻结

1. **发现。** 生成全部可构造条件的开发实例，各评估一次 P32/P0，最多 `24×64×2=3072` 次正常生成。按精度合并评估全部条件，理想无故障情况下只需两次模型启动；不能因分成 24 个条件而启动 48 次。
2. **选出确认对象。** 在发现集 BF16 正确率至少 `0.80` 的条件中按 `Δ_0` 降序选最多两个，之后依次按 BF16 得分更高、输入更短、记录更少、条件编号排序。不要求发现集已达到 `0.10` 才能确认，以免小样本初筛漏掉候选。若没有 BF16 达到 `0.80` 的条件，则取 BF16 得分最高的两个确认其可解性；BF16 达标候选只有一个时，不用明显不可解条件补足数量。
3. **两批新样本确认。** 每个候选生成两批各 512 个新实例，所有确认题均不属于发现集或正式数据。每批分别比较 P32/P0。只有两批均满足 `Q_B >= 0.80` 且 `Δ_0 > construction.min_fp8_gap`，该条件才算确认成功。最多 `2×2×512×2=4096` 次正常生成；同样按精度合并运行，不为两批额外重启。
4. **选择一个规则。** 若多个条件确认成功，优先选择两批中较低的 BF16 正确率更高者，再依次选输入更短、记录更少、条件编号更小者。达到恢复需求后不继续追求 P0 越差越好。
5. **冻结。** 保存所选任务、长度、记录量、提示、词表、背景来源划分、证据位置分布、评分、种子、阈值及两批确认结果，随后生成正式数据。确认阶段不搜索层、不观察正式测试输出。

两批确认直接检验用户要求的可解性与明显恢复需求，不额外要求开发集 CI 下界也超过 `0.10`。逐批与合并的分数、配对区间、错误类型及截断率均输出，便于判断离边界有多远。不能用合并均值掩盖某一确认批不达标，也不在确认失败后追加新批次直到通过。

正常错误答案、额外文字和截断输出保留并评分；临时通信错误不能当作答错来制造 FP8 退化。确认不完整时状态是中断或运行失败，不是构造成功或科学负结果。

若无人确认成功，本轮以 `construction_not_found` 正常结束，记录失败类别和全部已有证据，不进入自动选层、不自动切换位宽。粗筛但未确认的其他条件不被宣布已经排除。

### 5.4 数据独立性与评分

数据按 `discovery`、`confirmation`、`experiment`、`test` 四个阶段分配来源组，再生成新的映射、目标、位置和背景组合。自然文档统一 ID 与重复内容后，默认按来源种类分别分配约 `5%/5%/10%/80%`，小数余量给测试池；这只是背景池分配，题数由各阶段配额决定。

所有阶段的基础实例互不相同，同一基础世界的变体不得跨阶段。两个确认批也使用不同基础实例。不同题可以在同阶段随机复用背景，报告复用率；独立性和区间的解释以本次背景池为条件。背景不足时报告具体问题，不将正式测试池借给开发阶段。

模型输出只用一种预先固定的评分：提取完整、独立的六位十进制数字串，不能从更长的数字或字母数字标识中截取六位；去重后只有一个代码且等于真值时得 `1`，否则得 `0`。可接受包含唯一正确代码的短句或 JSON，不因轻微格式差异丢分。多个不同代码、错误代码、空输出均得 `0`；重复同一个正确代码仍得 `1`，但重复次数另行报告。评分不使用另一个模型。

不依据逐题 P32/P0 对错筛选正式数据，不把 v3.0 的 FP8 错题重新编号，也不将发现或确认样本充当选层数据。正式数据是冻结生成规则的全新抽样，所有产生的有效题都进入评分。

## 6. 接续 v3.0 自动选层流程

### 6.1 正式数据

构造确认后生成 `512` 条实验数据和 `4096` 条测试数据，正式数据共 `4608` 条，实验集占约 `11.1%`。均来自所选的一个任务族与一个长度条件；均分就是该条件下的正确率，不能伪造四任务或复制题目填满旧版 16 个单元。

实验顺序在运行任何混合候选前由数据种子固定，形成 `32→96→512` 嵌套前缀。相对 v3.0，首两级和晋级规则不变，末级随实验集扩到 512；这是评估样本量调整，不是重新设计选层算法。

正式测试的模型输出只在最终候选冻结后产生。不同条件的题不混合稀释分差；如果以后需要多任务分布，应另行预定任务、权重与样本数。

### 6.2 保留的算法行为

- 实验集先评估 P32 和 P0，以 `0.01/0.02` 质量容差判断是否需要搜索。即使构造确认曾显示明显缺口，也不能跳过这两个真实端点。
- P0 在新的实验集已符合原质量约束时，保持合法输出 P0 的行为，并报告构造确认与正式实验不一致；不强制加层、不重新抽实验题。
- P0 不可行时，从空集合开始、束宽 `2`，逐层扩展当前路径的所有剩余层，对相同集合去重，重新测量条件边际收益。
- 保留 v3.0 的约束排序、分阶段评估、并列/重采样软晋级和首个可行深度停止；`promotion_win_fraction=0.05`。
- 只有完整 512 条实验数据评估完毕的候选才可判为实验可行。之后沿用完整实验集上的反向删层。
- 默认选层与删层合计 `search.max_requests=24576`，复用已有回答；预算耗尽时只保留已经全量评估且可行的候选，不将部分候选补标为成功。
- 层集合在测试前写入冻结记录，之后用独立测试比较 P32/P0/S，相同配置去重。测试失败不反馈本次选层。

不增加随机十层补充搜索、人工指定“好层”、失败候选强制测试或另一套优化器。它们若需要研究，应作为后续方法对照，不能混入本版的数据构造主线。

理论容量沿用 v3.0：`C(S)/C(P32)=64/(32+|S|)`，目标 `1.5×` 对应最多保留 10 层。最终质量与容量均按真实测试结果判断；没有候选时沿用 v3.0 终止并报告的行为，不用回退 P32 计作优化成功。

### 6.3 质量结果与数据复现分别报告

| 字段 | 含义 |
|---|---|
| `construction_passed` | 两批独立确认数据均满足 BF16 可解性与 FP8 恢复需求 |
| `quality_passed` | 冻结候选在独立测试上满足 v3.0 质量容差 |
| `technical_goal_passed` | 沿用 v3.0：有效独立测试的质量与实测容量同时达标 |
| `data_conditions_reproduced` | 正式测试上再次观察到 `Q_B >= 0.80` 且 `Δ_0 > min_fp8_gap`；未做测试时为 `null` |
| `recovery_demonstrated` | 构造通过、正式数据条件复现、主目标达标，且候选为非端点混合配置 |
| `complete` | 本轮已经给出终局结果，包括构造未找到、搜索无解和质量失败；不表示优化成功 |

上述通过字段是对预定点估计约束的判断，不表示已经证明联合 95% 置信水平的非劣性。沿用配对、按来源组重采样的区间解释；正式报告另列 BF16 正确率和 P0 缺口的不确定性。全同结果或有效组不足时不能用零宽 bootstrap 区间声称总体误差为零。

独立测试中 P0 损失仍为 `0.08`、混合配置保质且有容量收益，可能使 `technical_goal_passed=true`，但 `data_conditions_reproduced=false`、`recovery_demonstrated=false`：本次没有完整复现预定的强恢复场景。P0 自身达标同样只说明原项目目标可能达到，不能用来证明混合选层的恢复价值。

## 7. 数据、运行与结果合同

### 7.1 最小产物

构造配置保存于 `configs/v4.0/quality.json`，原始来源可使用 `data/v4.0/source/` 或显式指定现有 `data/v3.0/source/`。实际生成文件与运行目录为：

```text
runs/v4-<run_id>/
  inputs/                         实际源码、配置、模板、数据与来源说明
  construction/
    discovery.jsonl               发现样本
    confirmation.jsonl            两个确认批的样本与 batch_id
    conditions.jsonl              全部条件、分数、不可构造原因与选择依据

  policies/<policy_config_id>/    各阶段原始回答与服务日志
  search-trace.jsonl               进入正式搜索后产生
  selection.json                  测试前冻结的层集合
  completed-manifest.json
  report/CONSTRUCTION-v4.zh-CN.md
  report/QUALITY-v4.zh-CN.md       进入正式实验后产生

  experiment.jsonl
  test.jsonl
  dataset-manifest.json
```

`selected-rule.json` 是传递真实构造规则的输入文件，不是需要人工签署、比对哈希或每次重跑开发获得的准入证书。一次构造通过后，原运行续跑直接复用其规则和缺失回答。

每条样本保留现有 `sample_id`、`source_question_id`、`source_group_id`、`split`、`task`、`length_bucket`、`user_prompt`、`expected_answers`、来源 ID、实际 token 数与评分版本，并增加 `condition_id`、`record_count`、`base_instance_id`、`batch_id`、证据位置与实际生成种子。正常回答保留完整文本与 `finish_reason`，不只保存提取代码。

### 7.2 续跑与失败

复用 v3.0 逐样本落盘、仅补缺失 ID、同配置缓存、损坏尾行恢复、真实 dtype/prefix/token 检查与失败日志导出。运行内部的输入识别可以继续自动使用现有标识机制；用户不需要运行额外摘要比对程序。

构造发现、确认与选层预算按各自阶段累计，重新执行命令不得重新抽题、重置已经确认失败的条件或从零计算搜索预算。已完成的正常错误答案不重试；临时 HTTP 错误最多一次自动重试。运行异常与没有找到合适数据分别记录。

源码 ZIP、服务器无 `.git`、服务器有 Git 但无远端都能执行；输入副本应在实际阶段开始时保存。只导出某个 v4 运行时，必须同时带出其发现、确认与正式实验上下文，不能只留下“构造通过”布尔值。

跨运行已使用测试的记录延续现有语义，v3/v4 目录都应被检查，避免通过更换版本前缀绕过记录。新构造可以复用公开来源包，但不能复用旧题、旧回答或把看过的新测试重新称为独立测试。

## 8. 预算、终止与后续方向

| 阶段 | 无通信重试时的生成次数上限 |
|---|---:|
| 24 条件发现：24×64×2 | 3072 |
| 两条件、两批确认：2×2×512×2 | 4096 |
| 正式实验端点：512×2 | 1024 |
| 束搜索与删层 | 24576 |
| 正式测试：4096×3 | 12288 |
| **完整路径合计** | **45056** |

构造不成功时最多进行前两阶段，正常生成上限 `7168` 次。不可构造条件、仅一个确认对象、P0 早停或提前找到可行层集合都会减少开销。通信重试另列；搜索的请求预算按实际请求计数，包含重试，不能把所有阶段的回答总数误称为搜索开销。

GPU 时间与输入长度、加载和服务器速度有关，本版记录实际秒数、启动次数与 token 数，不承诺固定小时数。每轮预算在运行前配置并保存，构造轮的实际成本可用于安排后续资源；续跑沿用该轮累计预算，不在看过正式测试之后追加同一轮搜索。

| 终局 | 解释与后续方向 |
|---|---|
| BF16 可解性未确认 | 改进任务、提示或降低任务负担；降低 KV 位宽不能修复 BF16 本身的问题 |
| BF16 可解，但没有确认到超过 `0.10` 的 FP8 缺口 | 在本范围和预算内未交付强恢复需求数据，可考虑转向更低位宽 KV |
| 确认两批不一致或区间很宽 | 保留不稳定或证据不足的结论；不逐题筛选或无限补批 |
| 数据确认成功，搜索没有可行解 | 数据前两条件与混合可恢复性不同；不能推断数据不存在或束搜索普遍无效 |
| 实验可行，测试失败 | 当前选择未通过新数据验证；保留失败，后续新实验使用新测试 |
| 数据条件复现且混合配置达到质量与容量目标 | 交付生成器、冻结规则、层集合和完整证据，限定到当前任务分布与环境 |

v4.0 不实现 FP4 或自动修改量化格式。若转向四位 KV，需要单独确认当前 GPU、模型、逐层 BF16 保留与真实压缩存储的支持；FP4/NVFP4/INT4 不是同一种格式。此前核对的 vLLM/FLASHINFER NVFP4 KV 路径要求 SM100，不能承诺在现有 A6000 上只改 dtype 就能运行。[vLLM 支持代码](https://docs.vllm.ai/en/latest/api/vllm/v1/attention/backends/flashinfer/#vllm.v1.attention.backends.flashinfer.FlashInferBackend.supports_kv_cache_dtype)

## 10. 交付与证据边界

本版实现完成应交付生成器、有限难度扫描、两端确认、v3.0 算法适配、独立测试、续跑、失败导出与离线运行手册。本次工作范围为设计和计划，后续实现按[分阶段计划](IMPLEMENTATION-PLAN.zh-CN.md)推进。
